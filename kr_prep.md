# Подготовка к контрольной работе

## 1. Когда я выберу rebase, а когда merge? Почему?

**Rebase** выбираю, когда:
- Работаю в личной (непубличной) ветке.
- Хочу получить линейную, чистую историю без merge-коммитов.
- Перед созданием Pull Request нужно «подтянуть» свежий main.
- Хочу «причесать» свои коммиты (squash, reword).

**Merge** выбираю, когда:
- Ветка публичная, с ней работают другие люди.
- Нужно сохранить полную историю разработки.
- Сливаю feature-ветку в main — важно, чтобы история не переписывалась.
- Есть риск потерять коммиты при rebase.

**Кратко:** rebase — для локальной чистки, merge — для публичных веток.

## 2. Что произойдёт, если я сделаю rebase публичной ветки?

Rebase переписывает историю: создаёт **новые** коммиты с другими хешами и удаляет старые.
Если ветка уже запушена и коллеги на неё опираются:

- У них останутся старые коммиты, у меня — новые.
- Их `git pull` вызовет конфликты или создаст дубли коммитов.
- При `git push` потребуется `--force`, что перезапишет историю на сервере.
- Коллеги потеряют свои локальные изменения, если не сделают `git pull --rebase`.

**Золотое правило:** never rebase public branches.

## 3. Зачем нужен multi-remote?

**Multi-remote** — это настройка нескольких удалённых репозиториев для одного локального проекта.

**Сценарии:**

1. **Зеркало / бэкап.** GitHub + GitLab.
2. **Open Source / Fork.** `origin` — мой форк, `upstream` — оригинал.
3. **Разные команды** на разных платформах.
4. **Миграция** с одного хостинга на другой.
5. **CI/CD** — разные remote для staging и production.

git remote add gitlab git@gitlab.com:user/repo-mirror.git
